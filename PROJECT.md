# PROJECT.md

dockvmap ("Docker Virtual Mapper") is a Docker/OCI registry proxy: clients pull through a stable "virtual tag" (`myimage:current`) transparently mapped to a real upstream tag tracked per-image. One binary runs a proxy server (OCI Distribution API), a web server (REST management API + embedded frontend), and a background worker, sharing one SQLite DB and one registry HTTP client.

## Principles

A professional app that is useful, intuitive, secure and fast, without being over-engineered. These rules apply to anyone changing the project, human or AI:

- **Useful, not a gimmick.** Every feature solves a real problem for someone running dockvmap. If its value isn't obvious, it doesn't ship.
- **Intuitive.** A feature is clear from the UI without reading docs: plain wording, sensible defaults, and errors that say what to do next.
- **Secure by default.** Least privilege, read-only wherever possible, validate every input, never send or log secrets.
- **Fast and light.** No needless work on hot paths; background features never touch the proxy request path. Measure before and after changes that add load.
- **Not over-engineered.** The simplest design that is correct. No abstractions, options or layers for hypothetical needs, and no code, tests or guards for edge cases a real homelab or small DevOps setup won't hit.
- **Reuse first.** Before writing a helper, component, style or test fixture, find the existing one. One rule lives in one place.
- **Tidy and readable.** Clear names, small functions, no clever tricks. No dead or commented-out code, and no hacks: fix the cause, not the symptom. When a change leaves something unused (a helper, field, type, style or API field), remove it in the same change.
- **Respect the layers.** `store` → `service` → `web` / `proxy` on the backend; `lib/api` / `lib/stores` / `lib/services` on the frontend; the agent imports only `internal/agentapi` and the standard library.
- **A live production app.** Config, API and database compatibility matter. Migrations are forward-only and come with a backup note; refactors keep behaviour identical.
- **Match the surrounding code.** Same naming, idiom and formatting. No comments explaining design rationale (it belongs in this file); no em dashes in UI, code, docs or commits.
- **Verify honestly.** `make verify` plus end-to-end checks (headless browser at desktop and phone widths) on scratch data, never on real data or config. Failures are reported as they are.

## Process model

### Runtime shape

`main()` → `run() error`. `run()` is a dispatcher: it does shared bootstrap (config, logging, data dir, credential key), then either handles a one-off CLI command or calls `serve()`.

`serve()` is the full service composition root and lifecycle. It builds the store, the service layer, then three long-lived components off one shared `*http.Client` and one `*sql.DB`:

- **proxy server**: OCI Distribution API (`/v2/...`).
- **web server**: REST API under `/api/` + the embedded frontend.
- **background worker**: independent scheduled jobs (see [Background worker](#background-worker)).

### Layering

`internal/store` → `internal/service` → `internal/web` / `internal/proxy`: strict and one-directional, SQL → business logic → HTTP. `internal/oci` stays decoupled from `store`/`service` via small interfaces; `cmd/dockvmap/adapters.go` holds the adapters that bridge them.

### Startup and dispatch

`run()` order: bootstrap → `-backup` (before `store.New`, since it opens the DB read-only and must snapshot the schema as-found) → a `switch` over the remaining one-off commands vs `serve()`. Startup failures `return` rather than `os.Exit`-ing past deferred cleanup.

**One-off CLI commands** (`cmd/dockvmap/commands.go`) each build only the minimal service subset they need and exit without starting any server:

- `-reset-password <username>` runs `Users.ResetPassword(ctx, username)`: look the user up by username, generate a random password, invalidate all their sessions, print it. Takes a username (not "the one user") so it stays correct if multi-user is ever added.
- `-refresh-tags` runs `Images.RefreshAll(ctx)`, the same one-shot sweep the worker runs on its ticker, exposed for scripting an out-of-band refresh. Partial failures don't abort the batch; joined per-image errors are returned (non-zero exit) after the refreshed count is printed.
- `-backup <path>`: opens the DB via `store.OpenForBackup` (no migrations; the newer-schema guard still applies), calls `Store.Backup` (`VACUUM INTO`, consistent while running, refuses if the target exists), and prints what else a restore needs (the credential key file/value, and `config.yaml`). No `-restore`; that's a documented stop/replace/start procedure.

### Shutdown

Listener failures go through a `serverErrs` channel into the same graceful-shutdown path as a SIGTERM, never a direct `os.Exit`; `awaitShutdown` then returns that error, so `main` logs it once and exits with 1, while a SIGTERM exits with 0. On shutdown, `awaitShutdown` cancels the worker context and waits for the worker goroutines, but only up to `workerShutdownTimeout` (10s): a hung job logs a warning and shutdown proceeds rather than blocking until the runtime SIGKILLs.

## Architecture

Package catalog. Deep dives for `taganalyzer`, image tag refresh, and tag discovery are in [Design Details](#design-details); the worker is in [Background worker](#background-worker); frontend is in [Frontend](#frontend).

- **`cmd/dockvmap`**: `main.go` (entry + flag parsing + shared bootstrap + dispatch), `serve.go` (`serve()`), `commands.go` (the one-off CLI commands), `server.go` (HTTP server construction, TLS, graceful shutdown), `worker.go` (background worker), `bootstrap.go` (`initBlobCache`/`initMailer`/`initNotifications`/`resolveCredentialEncryptionKey`), `adapters.go` (adapters keeping `internal/oci` decoupled from `store`/`service`). Lifecycle details in [Process model](#process-model).

- **`internal/config`**: `Load()` merges env > file > `default:` tag (env/defaults applied by reflection over struct tags). The file is decoded with `KnownFields(true)`, so an unknown or misspelled key is a startup error, not a silent no-op (env vars stay permissive). `applyDerivedDefaults()` normalizes interdependent settings (e.g. `tls.enabled` with a blank cert/key path flips off; `secure_cookies` defaults on when `tls.enabled` or `trusted_proxies` is set) and appends a human message to `Config.DerivedWarnings` for each adjustment, plus one when `trusted_proxies` is empty (client IP will be the immediate TCP peer). `main()` drains and `slog.Warn`s the warnings once logging is configured (`GET /api/system/status` re-exposes `Config.DerivedWarnings` in the UI, since they otherwise scroll away). The web server binds `web_server_https_listen` when `tls.enabled`, else `web_server_http_listen`; the proxy always binds `proxy_server_listen`, switching only its scheme. `proxy_access_log` (`*bool`, `default:"true"`, helper `ProxyAccessLogEnabled()`) is the "default on, override off" pattern like `blob_cache.enabled`; `serve.go` wraps the proxy handler in `httpmw.AccessLog` only when it is true.

- **`internal/store`**: SQL layer. `store.New` = `open` + `migrate`; `store.OpenForBackup` = `open` + `verifySchemaVersion` only. `open` also `chmod`s the DB file to `0o600` (it holds password hashes, session tokens, encrypted creds); `main()` creates the data dir `0o700`.

- **`internal/store/migrations`**: numbered, checksum-verified schema migrations. `verifySchemaVersion` (run by both `migrate()` and `store.OpenForBackup`) refuses to proceed when `MAX(schema_migrations.version)` exceeds the highest bundled migration, so an older binary won't silently run against, or back up, a schema a newer build created. Migrations are forward-only and safe on a populated DB.

- **`internal/service`**: business logic. Multi-dependency constructors take a config struct, not positional args: `NewImages(ImagesDeps{…})`, `NewDiscoveries(DiscoveriesDeps{…})`.

- **`internal/proxy`**: OCI Distribution API (`/v2/...`); resolves virtual tag → real registry/repo/tag, forwards to upstream, optionally through `internal/blobcache`. Basic-Auth gate on every request when `proxy_auth.enabled` (see `proxy_tokens.go`). When `proxy_access_log` (default true) the proxy handler is wrapped in `httpmw.AccessLog("proxy", …)` in `server.go`, which emits one structured `slog` line per request; the handler feeds it the resolved details (virtual image, upstream registry/repo/tag, digest, cache hit/miss, auth outcome) through a pointer stashed in `context.Context` (`httpmw.AccessFieldsFrom`), and the middleware adds status/bytes/duration. The per-request `slog.Info` tracing lines already in the handler are separate and unaffected by the toggle. The middleware logs `r.RemoteAddr`, raw `X-Forwarded-For` and `client_ip`, resolved with the same `trusted_proxies` set as the web UI (`httpmw.ClientIP`; `serve.go` parses the setting once and passes it to both servers). A successful manifest or blob `GET` is reported to `service.ProxyUsage`, and so is a new digest served for the image's tag (see below). With `internal_registry.enabled`, names that aren't virtual images are passed through to the internal registry, pushes included; see "Internal registry" in Design Details. `proxy.New` takes a `proxy.Deps` struct.

- **`internal/web`**: REST API + embedded frontend (`handler.go`). `GET /health` is intentionally outside `/api/`'s auth middleware; it runs a real `SELECT 1` (`Store.Ping`, not the driver's connection-only `PingContext`) and returns `{status, version}` so deploy checks can read the running version without authenticating. The embedded frontend is served with `Cache-Control: immutable` for content-hashed `/assets/*` and `no-cache` for `index.html` / the SPA fallback, so a deploy can't leave a stale index pointing at gone asset hashes. `GET /api/proxy-metrics` is deliberately kept with no frontend caller - the dashboard reads it through `GET /api/dashboard` - so don't prune it as dead code.

`GET /api/events` has three callers: the dashboard's `activity` section, the Tag activity page (`/tag-activity`), and the "Upstream tag activity" section on `ImageDetails` (`lib/components/TagActivitySection.svelte`, last 10 for one image). It takes the same `type` / `since` / `until` filter params as `/api/audit-logs` plus an `imageId`; both endpoints return a list + `total` and share the `parsePagination` + `whereBuilder` + `List`/`Count` pattern (`model.ImageEventListFilters` mirrors `model.AuditLogListFilters`). The Tag activity page has no image picker - `imageId` is only ever set by deep-link (the ImageDetails section's "View all" link, `/tag-activity?imageId=X`), surfaced as a clearable chip; same rationale as the audit log having no per-entity filter.

`GET /api/failures` (was `/api/recent-failures`) is the same filtered/paginated pattern again (`source` / `since` / `until` + pagination, `{failures, total}`), feeding both the dashboard `issues` section (limit 5) and the System > Failures tab. `FailureLog.Recent` was replaced by `List`/`Count` + `model.BackgroundFailureListFilters`.

**System section:** `internal/web/api_system.go` serves `GET /api/system/status` (version, DB reachability + schema version + file size, process start time, `Config.DerivedWarnings`, virtual tag, resolved `trusted_proxies`, `proxy_auth.enabled` - a curated set, never the full config or any secret), `GET /api/system/tasks` (the worker job catalog merged with `worker_ticks` run history, see [Background worker](#background-worker)), and `POST /api/system/tasks/{name}/run` (a generic manual trigger via `service.Worker.Trigger`, `404` when the job is not triggerable). The frontend is `routes/System.svelte`, a `/system/:tab` shell over `lib/components/system/{Status,Tasks,Failures,Audit}Tab.svelte`. The audit log moved here: `/audit-log` is gone (no redirect), and `AuditTab.svelte` is the former `AuditLog.svelte` body with `pushListQuery("/system/audit", …)`.

`GET /api/registries/test` and `POST /api/registries/{id}/test` (`apiTestRegistry` / `apiTestExistingRegistry`) run a live `GET /v2/` + auth handshake for the "Test connection" button in the create/edit registry modals. `{id}/test` uses the registry's stored credentials unless the body overrides them (the pointer-pair `username`/`credential`, both nil = use stored). A failed handshake returns `200 {ok:false,error}` (a real answer, not a server error); only a malformed request is `4xx`. `service.Registries` gained a `RegistryConnChecker` interface (implemented by `registryConnCheckerAdapter` in `cmd/dockvmap`, which builds a throwaway `oci.Client` with static providers so it can test unsaved values without disturbing the shared client's per-host caches). `NewRegistries` now takes `RegistriesDeps{Store, Audit, ConnChecker}`.

  **Client IP resolution:** `withRequestInfo` (the outermost `/api/` middleware) resolves the real client IP once via `trusted_proxies` and stores it in `context.Context` (`service.RequestInfo`); every downstream consumer (audit log, login rate limiter) reads that, never `r.RemoteAddr`/`X-Forwarded-For` directly. `httpmw.ClientIP` trusts `X-Forwarded-For` only when the immediate TCP peer is itself in `trusted_proxies`, then walks the header right-to-left skipping trusted hops. `trusted_proxies` entries are IPs/CIDRs, plus the literal token `gateway`, resolved once at startup (`httpmw.ParseTrustedProxies`, called in `serve.go` for both servers) to the container's IPv4 default gateway (parsed from `/proc/net/route`), the address a proxy's traffic is SNAT'd to under Docker's default bridge + published port. Mixed lists are fine (`["gateway", "10.20.45.23"]`). The deployment gotcha around append-vs-passthrough `X-Forwarded-For` is in [Traps](#traps).

- **`internal/ipmatch`**: parses `[]string` IP-or-CIDR config lists into a matchable `Set`; shared by `trusted_proxies` (`internal/httpmw`) and the login rate limiter's `bypass_ips` (`internal/service`) so both interpret entries identically. The `gateway` token is expanded before `ipmatch.Parse` sees it.

- **`internal/httpmw`**: HTTP middleware shared by the web and proxy servers. `Recover` wraps both handlers in `server.go`: a handler panic is logged via `slog` with method/path/remote/stack and turned into a `500` if nothing was written yet, instead of a dropped connection. Its `recoverWriter` forwards `Flush`/`ReadFrom`/`Unwrap` so proxy streaming and `http.ResponseController` still work. `http.ErrAbortHandler` is re-raised untouched, since `httputil.ReverseProxy` panics with it when a client disconnects mid-transfer and it isn't a crash. Both writers ignore interim `1xx` statuses (a `100 Continue` from a passed-through upload), so the final status is the one logged and a later panic still answers `500`. `ClientIP` (`clientip.go`) and `ParseTrustedProxies` (`gateway.go`, the `gateway` keyword) live here too, shared by the web server and the proxy.

- **`internal/oci`**: registry HTTP client: auth challenge flow, Docker Hub compat. `Client` holds the HTTP client + the two provider interfaces; all per-registry-host caching (bearer tokens, resolved credentials/options, cert-relaxed HTTP clients) lives in `registryCache`, whose `cachedFetch[V]` helper does LRU-check → singleflight → fill so a burst of misses triggers one fetch. `do` retries `429`/`503` up to 3 times (4 attempts total) with a context-aware wait: `Retry-After` when present and capped at 30s, otherwise `1s`/`2s`/`4s` backoff plus jitter. An exhausted retry returns the last response as-is, still surfaced through `registryStatusError` → `*oci.Error`. All registry calls are `GET` with no body, so re-sending is safe.

- **`internal/taganalyzer`**: pure tag-string analysis (`tokenize → classify → family → order`), no I/O. Determines family grouping, tag ordering, family relevance, and whether an upgrade is available. Deep dive: [Design Details → taganalyzer](#internaltaganalyzer).

- **`internal/tagfilter`**: loads tag exclusion regex patterns from `filters.yaml` and exposes `Filter.Apply(tags) []string`. With no configured `tag_filters_path` it uses embedded defaults: `^commit-.*`, `^pr-.*`, `^sha256-[0-9a-f]{64}`. Patterns match case-insensitively (so `^pr-.*` also covers `PR-`). The digest pattern intentionally has no end anchor, since a tag starting with a full SHA-256 digest is a cosign artifact regardless of any `.sig`/`.att`/`.sbom` suffix. Tags are filtered once, at the point they're fetched, then passed downstream as already-filtered data; no later layer re-applies the filter, and filtering never happens inside `internal/oci` (transport stays independent of tracking policy). Kept separate from `internal/taganalyzer` (which stays I/O-free) and from runtime config (this is policy, in its own file).

- **`internal/blobcache`**: optional on-disk manifest/blob cache, keyed by digest. `Cleanup` (worker job) first drops blobs untouched for `blob_cache.lifetime`, then, if `blob_cache.max_size` is set, evicts least-recently-accessed blobs (file + row) down to 90% of the cap, a low-water mark so it doesn't evict on every run at the limit. Enforcement is async-only (bounded by the cleanup interval); the running byte total is decremented locally during eviction since `Cleanup` holds `c.mu` and `writer.commit` takes the same lock. `Usage(ctx)` (used/max bytes) feeds the dashboard. `parseBytes` in `internal/config` is 1024-based; `""`/`0` = unlimited. The stored row type is `model.CachedBlob` so `internal/store` doesn't import `internal/blobcache` back; `blobcache` depends on `store` only through its own `Store` interface.

- **`internal/smtp`**: minimal `net/smtp`-based mailer for tag-change notifications. HTML mails are `multipart/related` wrapping a `multipart/alternative` (text + HTML) plus the DockVMap logo (`assets/dockvmap-logo.png`, `//go:embed`) as an inline `Content-ID: <dockvmap-logo>` part; `tag_notification.html` references it as `cid:dockvmap-logo`, so the branded header renders without an external fetch or a data URI (both blocked by major clients).

- **`internal/service/notification_digest.go`**: builds the two digest emails from all pending events in one run: updates available (to every recipient with a level) and tag changes, new and removed (to level `all` only). Only sweeps create `notify = 1` events, manual refreshes are `EventSilent`. A group's members with the same tags collapse to one line; a partial set names its images. A failed send is recorded in `background_failures` and the events are still marked sent, since the Updates page still shows them.

- **`internal/webhook`**: minimal HTTP POST client for tag-change notifications (`webhooks` config, a list of URLs). Sends dockvmap's own fixed JSON shape (`event`/`imageName`/`tags`/`updateAvailable`/`occurredAt`), deliberately not Slack/Discord-formatted; no per-provider formatting is built in, since there was no expressed need and it'd be the kind of speculative feature this project avoids. `service.Notifications` treats email and every webhook URL as independent, best-effort, attempt-once channels per event, with no per-channel delivery tracking (`tags_events.notif_sent_at` is a single flag), so a down channel loses that one notification silently (logged) rather than blocking or duplicating others. The worker runs when `smtp.enabled` **or** `webhooks` is non-empty.

  Event types on `tags_events` are `TAG_ADDED`, `TAG_REMOVED`, `UPGRADE_AVAILABLE` (emitted by `RefreshAvailableTags` via `Events.HandleEvent` when an image's `updateAvailable` flips true or its target advances). A pinned image (`images.pinned`) never emits `UPGRADE_AVAILABLE` because `effectiveUpdateAvailable` forces its `updateAvailable` to false; `TAG_ADDED` / `TAG_REMOVED` are unaffected. Webhooks fire for every event. Email is gated per account by `UserPreferences.NotifyLevel` (`all` / `upgrades` / `none`, default `all`; fresh admin gets `upgrades`; legacy `notifyNewTags` true/false maps to `all`/`none` on unmarshal): `upgrades` sends only `UPGRADE_AVAILABLE`, `none` nothing, `all` everything. The gate is applied at send time in `SendPendingTagNotifications` (per recipient, via `mailTargets`); `tags_events.notify` still just means "not a silent refresh".

- **`internal/service/failure_log.go`** (table `background_failures`): `FailureLog`, a persistent log of actionable background failures (webhook/email delivery, image tag-refresh, discovery, event registration, digest lookup), injected into `Images`, `Notifications`, `Discoveries` alongside their existing `slog.Error` calls (both fire: slog for the ops trail, this for the GUI's "Recent issues" card). `Record(ctx, …)` inserts on a `context.WithoutCancel` + 5s timeout so a timed-out refresh still logs its failure; a failed insert is swallowed with a `slog.Error`. `List(ctx, filters)` / `Count(ctx, filters)` (`model.BackgroundFailureListFilters`: `source` + date range + pagination, same `whereBuilder` pattern as audit/events) back `GET /api/failures` and the System > Failures tab, one row per occurrence. The dashboard `issues` section (limit 5, `{failures, total}`) uses `LatestDistinct(ctx, limit)` instead: the newest row of each identical source + detail + error, with its `occurrences` count, so one check failing every day can't push other failures off the card; `total` still counts every row. A 24h `background-failure-cleanup` job drops rows older than 30 days (`occurred_at` is `DEFAULT CURRENT_TIMESTAMP`, so the prune binds via `sqliteDatetime()`). Same reasoning as `tags_events` existing separately from `image_tags`: a dedicated event log decoupled from the current-state tables, so a since-resolved transient failure (e.g. `images.last_check_error`) doesn't just vanish from view, and now survives a restart. `internal/web` composes the human-readable message per source (`failureMessage` in `dto.go`) from the stored raw error text, kept verbatim, since that's the useful troubleshooting content.

- **`internal/service/proxy_tokens.go`** (table `proxy_tokens`): CRD-only (no update, no revoke-vs-delete distinction), issued by the single admin, not tied to a `user_id` (matches `registries`/`images`, which also carry no creator column; provenance lives only in the audit log). Token stored as a SHA-256 hash (fast, not bcrypt: a high-entropy random secret, not a human password); plaintext shown once on creation, never retrievable again. Enforced in `internal/proxy` via HTTP Basic Auth on every `/v2/...` request, gated by `proxy_auth.enabled` (config, default `false`: an explicit switch, not "on the moment a token exists"). Only the password field is checked; the username is free-form/unchecked (label-not-identity: any client presents any username, e.g. `docker login -u <label> -p <token>`). A successful `Verify` records the token's use in `ProxyUsage`, which feeds `proxy_tokens.last_used_at`; the Proxy Tokens page shows it only while `proxy_auth.enabled`, with a warning once it is more than 90 days old. A token with no recorded use gets no warning, since tracking only started with migration `030`. `can_push` (migration `035`) is chosen at creation only; `Verify` returns the matched token so the proxy can check it and audit pushes under its label.

- **`internal/store/proxy_metrics.go`** (table `proxy_metrics_daily`, `day` TEXT PK in UTC) + **`internal/service/proxy_metrics_history.go`**: `proxy.Metrics` stays an in-memory atomic counter set; the `proxy-metrics-flush` job folds `Snapshot() − prev` into today's row (`RecordDelta` → `INSERT … ON CONFLICT DO UPDATE col = col + excluded.col`), and its `onShutdown` does a final fold. `prev` advances only on a successful write, so a failed flush retries the whole delta. `ProxyMetricsHistory.Summary` reads the last 30 rows and sums them into `today` / `last7d` / `last30d` windows (server-side, one query) for `GET /api/proxy-metrics` and for the `metrics` section of `GET /api/dashboard`, both of which also carry `cache.{usedBytes,maxBytes}` from `blobcache.Cache.Usage` (omitted when the cache is off). The dashboard reads the aggregate; `/api/proxy-metrics` is kept but has no frontend caller. `proxy-metrics-cleanup` prunes rows older than 30 days.

- **`internal/service/proxy_usage.go`** (`images.last_pulled_at` / `last_pulled_tag`, `proxy_tokens.last_used_at`, migrations `030` and `033`): when a client last fetched an image and which real tag that was. A `GET` of a manifest or a blob is a pull; a `HEAD` records nothing, because Docker sends one just to check. So a pull that downloads nothing is not recorded either: after rolling back to a version the hosts still have, the image keeps showing "Not pulled since the tag changed" until something new is pulled, while Running on shows what actually runs. Blobs must count: Docker with the containerd image store sends a manifest `HEAD` and fetches everything else through `/blobs/`, so it never sends a manifest `GET`. A `GET` counts only once the whole response reached the client. A digest reference, which every blob is, records the image's current tag, so a blob pull of an older tag through the proxy shows as the current one. What actually runs comes from the agent. The proxy records into an in-memory map (one entry per image, per token and per newly served tag digest, see Current digest; a mutex-guarded write, nothing touches the database per request); `proxy-metrics-flush` saves it in one transaction every 5 minutes and on shutdown, clearing the map only after a successful write and merging it back on failure, so a hard crash loses at most 5 minutes. `GET /api/images`, `GET /api/images/{id}`, `GET /api/image-groups`, `GET /api/image-groups/{id}` and `GET /api/proxy-tokens` overlay unsaved entries on read, so a pull shows within seconds. `GroupPullNotice` (Groups page row and the image's Group row) warns when some members are not pulled on the group's tag (`groupPullStatus` in `lib/utils/groupPulls.ts`); it stays hidden until at least one member has a recorded pull. Writes never touch `updated_at`. No client IP is stored, since the proxy does not resolve `trusted_proxies`.

- **`internal/store/worker_ticks.go`** (table `worker_ticks`) + **`internal/service/worker.go`**: one row per `scheduledJob.name` holding `last_run_at` plus `last_error` / `last_count` (migration `026`, both nullable), all written by a single `RecordWorkerRun` upsert after the run (`context.WithoutCancel` + 5s), so the schedule survives restarts and the row carries the real outcome. A returned error and a recovered panic both advance `last_run_at` and record the reason; only a shutdown mid-run skips the write, leaving the previous tick in place. Separate from `images.last_checked` by design: it records when the tag-refresh job last swept, not per-image freshness. `service.Worker` is a pass-through service (like `Health`) that also holds the in-memory job catalog and trigger channels, keeping cmd → service → store layering. The migration doesn't seed rows; on first startup each job has none and runs once (staggered), then falls into its normal `interval`. `GET /api/tag-refresh-status` reads the `image-tag-refresh` row (`service.WorkerJobTagRefresh`, the one job name shared across packages) plus `tags_check_interval`, feeding the dashboard's "Tag checks" tile and the sweep button on `Images.svelte`. It stays a separate endpoint rather than folding into `GET /api/dashboard`, because the frontend polls it every 2s while a sweep runs (see [Frontend](#frontend)). `Worker.Ticks` (all rows) + `Worker.Catalog` (the static job set, see [Background worker](#background-worker)) back `GET /api/system/tasks`.

- **`internal/service/login_rate_limiter.go`** (`login_rate_limit` config): per-IP failed-`/login`-attempt counter, checked as the first line of `Sessions.Login` before any DB lookup or bcrypt work. State is an attempt count in an `expirable.LRU[string, int]` keyed by resolved client IP, TTL = `window`: a failure calls `Add` (renews the TTL), a block-check only `Get` (never renews), so the lockout is a flat `window` from the failure that tripped it, not extended by knocking while locked, and a quiet IP ages out on its own with no cleanup job. A successful login clears the entry. `bypass_ips` (also `internal/ipmatch`) skip the limiter entirely, still need the correct password. Defaults to enabled (`Enabled *bool`, not plain `bool`) so a `config.yaml` predating this feature is still protected after an upgrade, unlike the other opt-in blocks where the zero-value default is intentionally off.

- **`internal/service/discoveries.go`** (table `tag_discoveries`): backs the "Add virtual image" wizard's repository step. Deep dive: [Design Details → Tag discovery](#tag-discovery).

- **`internal/service/images.go`**: virtual image CRUD, tag changes, and the `images.pinned` toggle (`SetPinned`). **`images_refresh.go`** (same package) holds the tag-refresh pipeline, the per-image refresh lock and update detection. Deep dive: [Design Details → Image tag refresh](#image-tag-refresh).

- **`internal/service/image_groups.go`** (table `image_groups`, nullable `images.group_id`): group CRUD and the shared-version rules, as more methods on `Images` so they share its store and refresh locks. Deep dive: [Design Details → Image groups](#image-groups).

- **`internal/service/hosts.go`** and **`hosts_poll.go`** (tables `hosts`, `host_containers`, migrations `032` and `034`), **`internal/agentapi`**, **`internal/agentclient`**, **`internal/agent`**, **`cmd/dockvmap-agent`**: hosts and the read-only host agent. Deep dive: [Design Details → Hosts and the agent](#hosts-and-the-agent).

- **`cmd/tagaudit`**: offline auditing for `internal/taganalyzer`, run by hand, never by the app. Four modes over a corpus of cached tag lists (`-corpus`, default `sampledata/tags`): `-sample N` builds a repository list from Docker Hub's official images plus keyword search and picks the rest at random (written to `<corpus>/audit-manifest.tsv`); `-fetch` downloads tags for anything not cached; `-verify` re-checks every invariant the package promises plus determinism and placement accuracy; `-shapes` reports the segment shapes that stop tags from grouping; `-rank` flags repositories whose leading family looks wrong. No mode = all three reports. The corpus lives under gitignored `sampledata/`, so this command, not the data, is the durable artifact: a fresh clone regenerates everything with `-sample` then `-fetch`. `-shapes` is the one that finds *unknown* conventions: it describes each blocking segment by character class rather than content (`gb73411456155` and `ga16392559` both become `a{2-3}d{7+}`) and ranks buckets by volume × distinct-value rate. A high distinct rate means nearly every tag has its own value there, which is what a machine-generated identifier looks like; a named axis like `alpine`/`bookworm` reuses few values many times and sinks. High volume + high distinct rate + several unrelated repositories = a convention the analyzer doesn't understand yet (the signature `git describe` output had before it was handled, and Alpine's `-rN` would have had).

- **`cmd/taglist`**: prints the family breakdown for a single repository fetched live; the quick "what does this repo look like" tool, where `tagaudit` is the corpus-wide one.

## Background worker

`cmd/dockvmap/worker.go`. `serve()` calls `scheduledJobs(deps workerDeps)` once (synchronously) to build the full `[]scheduledJob`, then `worker.SetCatalog(jobDescriptors(jobs))` for the web layer, then runs the set in a goroutine via `runScheduledJobs`, which spawns each *enabled* job through `runScheduledJob`: **one goroutine, one `time.Timer`, one `select` per job**; never share one `select` across jobs.

### Job model

`scheduledJob{ name, description, interval, enabled, disabledReason, run func(ctx) (int, error), doneMsg, onShutdown, trigger }`:

- **Every job is always in the slice**, even when config disables it (`enabled: false` + `disabledReason`, e.g. blob-cache jobs when the cache is off). `runScheduledJobs` skips disabled ones (with a warn) but `jobDescriptors` still projects them into the catalog, so System > Tasks can show "Disabled: <reason>". Keep `scheduledJobs` producing one entry per job in both branches. `blobCacheJobs` / `proxyMetricsJobs` split out only to keep `scheduledJobs` readable.
- `run` is an inline closure calling the service method (the `counted` helper adapts `int64` counts). `executeJob` logs `doneMsg` with the returned count when it's > 0. Only `image-tag-refresh` keeps a named function (`runImageTagRefresh`), for its start/elapsed logging.
- `executeJob` runs `run`, then writes the tick once via `worker.RecordRun` (`context.WithoutCancel` + 5s), recording `last_run_at`, the count and any error text into `worker_ticks`. It also `recover()`s so one job's panic can't take down the worker; the recover path still records the tick with the panic as its error, so a panicking job advances its schedule instead of re-firing on every restart. A shutdown mid-run (`ctx.Err() != nil`) skips the write and leaves the previous tick.
- First fire = `max(0, interval - since(lastRun)) + stagger`, where `lastRun` is the persisted `worker_ticks` row (`service.Worker.LastRun`), so a process restarted more often than its `interval` still runs the job instead of resetting the clock. An overdue job runs once, not once per missed interval. Steady state is a fixed `interval` period, like `time.Ticker`. First-fire stagger is `10s × enabled-job index` capped at `30s`, first fire only.
- `onShutdown` (called on `ctx.Done()` with a `context.WithoutCancel` + 5s budget before the goroutine exits), used by `proxy-metrics-flush` to persist its last delta on a clean stop.
- `trigger` (`<-chan struct{}`, nil unless the job can run early on demand). A job registers its channel by calling `deps.worker.Register(name)` in `scheduledJobs`; that call is the single source of "which jobs are triggerable" (`jobDescriptors` reads `trigger != nil`). `service.Worker` has no fixed job list; `Register` creates the channel on first call, `Trigger(name)` returns false for anything never registered. Used by `image-tag-refresh` (the "refresh all tags" GUI button) and the two disk-reclaiming blob-cache jobs (System > Tasks "Run now"); `POST /api/system/tasks/{name}/run` is the generic trigger endpoint.
- `name` is the `worker_ticks` key; keep it stable and unique.

Tag discovery goroutines spawned by `Discoveries` are **not** tracked here: they run off the same worker context (cancelled on shutdown) but aren't in `runScheduledJobs`'s `WaitGroup`, so shutdown interrupts an in-flight scan rather than waiting; `Discoveries.RecoverFromRestart` cleans up the row on next startup.

## Frontend

`frontend/` - Svelte 5 + Vite + TS SPA, hash-routed (`svelte-spa-router`), cookie-session auth (not JWT, no `Authorization` header anywhere). `frontend/dist` is built and embedded at compile time (see [Commands](#commands)).

### State layering

`lib/api` (stateless fetch) → `lib/stores` → `lib/services` (only code that mutates a store). Only worth it once 2+ components share the same reactive data; otherwise page-local `$state` calling `lib/api` directly is fine and preferred.

Services are module singletons (`auth`, `dashboard`, `tagRefreshStatus`, `theme`, `toast`, `updatesCount`) **except** where the state belongs to one route, which gets a factory instead - `createTagDiscovery()` in `lib/services/tagDiscovery.ts` - so nothing leaks between mounts of that route. A singleton a route drives must expose a `start()` returning its cleanup, and reset its store there (see `dashboard.start()`).

### Conventions

- Every route component renders `<PageTitle title="…" />` (`lib/components/PageTitle.svelte`, a `<svelte:head><title>` wrapper appending `· DockVMap`). `ImageDetails` passes the loaded image name reactively. List/empty views can pass an `emptyAction` snippet to `AsyncState` to put the primary CTA inside the empty state.

- **Tabbed pages** (only `System` so far): route `/system/:tab` (plus a bare `/system` that the component redirects to `/system/status`), `routes/System.svelte` owns the `<AppShell>` + title + tab bar and `{#if}`-swaps a `lib/components/system/<Tab>.svelte`. Tab components render their own body only (no shell) and each own their data load. The one with URL-persisted list state (`AuditTab`) targets its own route path in `pushListQuery` (`/system/audit`).

- **Errors**: `lib/api/client.ts` is the only module that knows `ApiError` exists. `request()` catches the `fetch` rejection and rethrows a transport failure as `ApiError` (status `0`, "Could not reach the server…"), so "unreachable" and "server said no" are distinguishable instead of both landing in a generic fallback. Call sites never test `instanceof`: use `errorMessage(err, "Failed to …")`, whose fallback now only covers non-`ApiError` bugs.

- **Async state**: the loading → error → empty → content precedence lives once, in `lib/utils/asyncState.ts` (`resolveAsyncState({ loading, hasError, empty, busy })` → `{ kind, busy }`; `busy` is only ever true for `content`). Two presentations consume it: `AsyncState.svelte` (list/page - `TableSkeleton` or spinner, inline `.error`, `.empty` card) and `dashboard/CardBody.svelte` (cards - centred `CardState` blocks through `errorState`/`emptyState` snippets, `BusyOverlay` corner spinner). Both keep their own snippet-availability guards, so a missing snippet falls through to content. Add a state to the resolver, never to one of the two.

- **List pages**: guard rapid filter/pagination changes with an incrementing request token (see `Images.svelte`'s `loadToken`) so a slow superseded response can't overwrite a newer one. Track a `loaded` flag alongside `loading` and pass `AsyncState loading={loading && !loaded} busy={loading && loaded}`; skeleton on first load only; refetches keep current rows visible, dimmed with a corner spinner.

- **Sorting**: `createListView`'s optional `sortFields` (field → first-click direction) turns on sorting for a list. The sort lives in the same hash query as the filters (`sort` + `order`, so the back link from a detail page keeps it), is validated on read, stays out of `hasActiveFilters` and survives "Clear filters", and changing it goes back to page 1. `lib/components/SortableHeader.svelte` renders a sortable `<th>` with `aria-sort`; clicks cycle first direction → opposite → the list's default order. Only Virtual Images uses it so far (Name, Last checked, Last pulled, Update; Tag stays unsortable because version strings don't sort as text). Last pulled sorts by the saved value, so a pull from the last 5 minutes can sort as older until the next flush.

- **List-view persistence**: the hash query string is the single source of truth for a list page's filters + pagination. `lib/utils/listQuery.ts`: `readListQuery(defaults)` parses the flat filter object out of `location.hash`, coercing each key by its default's type; `writeListQuery(filters)` serializes back to a `?…` string (dropping empty / `false` / `0`); `pushListQuery(routePath, filters)` does a `history.replaceState` (no `hashchange`, so no reload loop); `watchListQuery(sync)` runs `sync` once and on every `hashchange`, returning a cleanup. A list page (`Images.svelte` / `AuditLog.svelte`) wires a local `syncFromUrl` (via `readListQuery`) into `onMount(() => watchListQuery(syncFromUrl))`, calls a local `syncToUrl` (via `pushListQuery`) on every filter change, and, where it has a detail route, appends `writeListQuery(...)` when navigating into a row. The detail page reads its own carried query once at init and echoes it onto the "← back" link (`backHref`). No storage, no sidebar coupling.

- **Row behaviour**: if a row has something to open, the whole row opens it and delete lives inside what opens (Virtual Images, Hosts, Groups, Registries, Audit). A row with nothing to open shows its action at the end (Proxy Tokens). Row actions are icons with a tooltip, never text, and badges only show status, so anything clickable must look clickable. Accent (blue) text is only for links: if it's blue it navigates, and plain values stay plain. Detail pages put each section in a card, ending with a Danger zone (`.danger-card`, `.danger-action`, `.danger-text` in `app.css`).

- **Filter bar**: wrap each labelled control in `<div class="filter-field"><span class="filter-label">…</span> …</div>` inside `<FilterBar>`; the search box goes in bare (no label). `FilterBar.svelte` owns the bar layout (compound `:global` rules keyed off `.filter-bar`). Every control carries `class="input filter-control"` (`.filter-control` in `app.css` is the compact toolbar treatment: 13px, `--radius-sm`, softer than a form `.input`). Add `class:is-active={<value set>}` so an engaged filter gets the accent border + tint. Selects render a custom chevron via the `--select-chevron` token; `select.filter-control` is auto-width with a `min-width` floor.

- **Phone layout**: the breakpoint is `768px`. `AppShell` turns the sidebar into a drawer behind a menu button, closed by Escape, the backdrop or a nav link. Pages stay usable through wrapping rules in `app.css` and `DetailRow`; tables keep scrolling inside `.table-wrap`.

- **Shared CSS primitives** (`app.css`): `.icon-button` (ghost square button; `.bordered` for the command-row copy variant), `.warning-box` (bordered warning callout, icon then text), `.notice` / `.notice-text` (accent status strip; `.warning` variant), `.modal-actions` (modal footer; `.split` for left and right groups with `.modal-actions-right`, `.spaced` outside a form), `.entry-list` / `.entry-card` / `.entry-main` / `.entry-meta` / `.entry-date` (bordered entry lists in the tag history and activity modals), `.row-link` (plain link that underlines on hover; color and weight stay local), `.table-actions` (right-aligned row buttons on a `<div>` inside the last cell, not on the `<td>`, since a flex cell stops stretching to the row height and its border breaks), `.clickable`, `.check-error-icon`, `.time-cell` (a date or relative time kept on one line, wrapping only on phones) and `.row-reveal` (table rows and cells; `.row-reveal` dims a secondary row action until the row is hovered or focused, only on devices that can hover), `.command` / `.command-row` (mono command/token box + copy row), `.list-header` (title-left / action-right row), `.table-wrap` (alongside `.card` on a list table's wrapper; `overflow-x: auto` so the table scrolls instead of clipping inside `.card`'s `overflow: hidden`), `.back-link` (the "← back" link above a detail page), `.detail-header` with `.header-actions` (a detail page's title and actions), `.heading-with-count` / `.heading-count` (a muted count in a card title), `.name-cell` (a name with its chip), `.group-label` (the small chip for a group or stack name; a `<button>` when clicking it filters), `.state-dot` (grey by default, `.running` / `.warning` / `.failed`; rendered with its label by `StateIndicator.svelte`). `.table td` is vertically centred globally. On phones table cells use `overflow-wrap: break-word`, so words stay whole and only a word wider than its column breaks; a cell of long unbroken values (URLs in failure messages, registry hosts) opts into `overflow-wrap: anywhere` locally, and a table too wide for a phone hides secondary columns with `.phone-hidden`, moving what still matters under the first cell with `.phone-only` (Hosts, Host details); `.input:disabled` dims + `not-allowed`. Keyboard focus: a baseline `button/a/[tabindex]:focus-visible` outline rule covers everything; components only need their own `:focus-visible` for a non-default look. Destructive/warning CTAs use `--btn-danger-bg` / `--btn-warning-bg` (fixed across themes) rather than `--color-danger` / `--color-warning`, which desaturate in dark mode. `index.html` carries a pre-bundle `#app-boot` spinner (literal hex mirroring the theme tokens) that `main.ts` clears before `mount`.

- **`Field.svelte`** (shared input) takes an optional `autofocus` prop that calls `.focus()` on the element in `onMount`, not the HTML `autofocus` attribute, which only fires on initial document parse, not on client-side navigation into a route (login reached after logout / session expiry / auth redirect). `Login.svelte` sets it on the username field.

- **Pollers**: `lib/utils/poller.ts` (`createPoller`) is the raw cancellable-interval primitive - a tick returning `false` stops the loop. `ImageDetails.svelte` uses it directly to poll `GET /api/images/{id}` every 2s while `refreshStatus === "running"` (merging each poll into `image` field-by-field via `mergeImage`, not reassigning, so a status-only tick doesn't churn child props); `lib/services/tagDiscovery.ts` and `lib/services/tagRefreshStatus.ts` own their own loops on it. `lib/utils/visibilityPoller.ts` (`createVisibilityPoller`) wraps it for anything that polls *while a page is open*: immediate first tick, `poller.stop()` on `visibilitychange` to hidden, resume with an optional `refetchOnResume` staleness predicate, and `start()` returns the stop function. `dashboard` and `updatesCount` use it. Prefer it over a bare `createPoller` for interval polling, so background tabs stay quiet.

- **Dashboard**: one request. `GET /api/dashboard` returns five sections (`summary`, `updates`, `issues`, `activity`, `metrics`), each a `{data, error}` envelope, so one failed query degrades one card instead of the page (`internal/web/api_dashboard.go` fans out with a `sync.WaitGroup`, each goroutine writing its own field). `Dashboard.svelte` is the only thing that fetches: `dashboard.start()` on mount, 60s visibility-gated poll, store reset on unmount. Cards are pure - they take `DashboardCardProps<T>` (`lib/components/dashboard/types.ts`: `{data, error, loading, busy, onRetry}`), and the `dashboardSections` derived store in `lib/stores/dashboard.ts` shapes each section into that contract, so the markup is `<RecentIssuesCard {...sections.issues} {onRetry} />`. Adding a card is a section server-side plus one line in the route; `hasErrors` iterates `Object.values(sections)` and needs no edit.

- **Tag refresh status** (`lib/services/tagRefreshStatus.ts`) is shared by `Dashboard.svelte` and `Images.svelte`, and deliberately stays *outside* the dashboard aggregate: it polls every 2s while a sweep runs, which a 60s aggregate must not. `watch()` refcounts watchers and returns an unwatch; concurrent `refresh()` calls coalesce onto one in-flight request. Poll failures are tolerated up to `MAX_CONSECUTIVE_POLL_ERRORS` (3), after which polling stops and `unavailable` is set - the "Tag checks" tile then reads *Unknown* rather than a stale *Running*, and no completion fires. Consumers must not hand-roll a `wasRunning` edge detector: `onCompleted(cb)` fires once when a sweep goes running → idle (`Dashboard` refreshes, `Images` reloads its table).

### Updates page

`routes/Updates.svelte` (`/updates`) is a review list of every image with `updateAvailable` set, separate from the Virtual Images list, which it does not touch. The header `UpdatesBadge`, the dashboard "Updates available" tile and the Updates card's "View all" link all point here; the `updateAvailable` filter on `/images` still exists. Each row is `lib/components/UpdateReviewRow.svelte`: `TagFamilyPicker` fed by `GET /api/images/{id}/tags?scope=newer` (`service.CurrentAndNewerFamilyTags`: the current tag's family, from the newest tag down to the current one by `tag_order`, with no other filtering, so prereleases and more-specific tags are offered and the admin decides). Its group-only parts (header, member chips, blocked notice) live in `lib/components/updates/`; the rows, the pull command and the Running on card of `ImageDetails.svelte` live in `lib/components/imageDetails/`, including `PullActivityRow` (last pull, a muted note when the pulled tag is not the current one). Both are display-only: state and API calls stay in the parent. The picker's `dimPrereleases` prop is off by default; this row and `ChangeTagModal` turn it on. As in `ChangeTagModal`, the row starts with the current tag selected and check-marked, and Update stays disabled until a different tag is picked, so a selected chip never reads as "what you are on" while meaning "what you will get". `updateAvailableTag` is shown as plain text next to the current tag. `TagFamilyPicker`'s `showFirstSeen` prop (here and in `ChangeTagModal`) puts when a tag was first seen in its tooltip, but only for tags first seen after the image's oldest one: tags from the initial scan all share that date, which says nothing about their real age. `searchable` adds a tag search once a list reaches `SEARCH_MIN_TAGS`. Because the current tag is in the list, the picker always stretches to reach it, so every newer tag is visible without "+N more". "All tags…" opens the regular `ChangeTagModal`.

A group with a flagged member is one row, using the same component with a `group` prop: `Updates.svelte` lists flagged groups (`GET /api/image-groups?status=updateAvailable`) above flagged ungrouped images (`GET /api/images?status=updateAvailable&ungrouped=true`). Groups come back complete and show on the first page only, so pagination stays image-based; the row drives everything through its first member, since the image endpoints already act on the whole group. A member with the newest tag missing shows up as a blocked row with a "Manage group" action. `UpdatesBadge` sums the same two totals and the dashboard tile uses the matching `ImageStatusCounts.UpdateAvailable`, so one group always counts as one update; `GET /api/images?status=updateAvailable` stays per image.

A row stays on screen after it is updated or pinned, with Roll back (`source: "restore"`) or Unpin, so rows are not reloaded out from under the user: `applyImage` merges fresh data into the list item, and a completed sweep bumps `reloadToken` and only reloads the list when nothing was cleared. Update, Roll back and Pin are disabled while a sweep or that image's refresh runs, because `UpdateTag` waits on the same per-image lock held through the upstream fetch. Cleared rows shift the server's offsets, so `changePage` moves back by that count and snaps to a page boundary: a few rows can repeat, none are skipped. Tag marks-as-seen happens on update rather than on load, otherwise opening the page would clear every new-tag dot. `ImageDetails` opened from here carries `from=updates` so its back link returns to the page.

### User-agent parsing

`lib/utils/userAgent.ts`: `parseUserAgent(ua?)` wraps the `bowser` dependency and returns `{ browser?, os?, device: "desktop"|"mobile"|"tablet"|"unknown", label, raw }`. `browser` is name + major version ("Chrome 140"); `label` joins the resolved parts ("Chrome 140 · Windows"), or is the raw string when Bowser can't identify the browser, or "Unknown device" when the UA is empty. `lib/components/DeviceIcon.svelte` maps `device` to a Lucide icon. Used by `Profile.svelte` (active sessions: icon + label, raw UA in `title=`) and `AuditLog.svelte` (audit detail: icon + label, raw UA shown beneath in muted text). Display-only; the backend stores and returns the raw UA untouched.

### Traps

- **Lucide icons**: import from the icon's own subpath (`@lucide/svelte/icons/x`), never the package root (drags ~3800 files into `svelte-check`). Never pass `class` directly to an icon component; it's invisible to the parent's scoped CSS; wrap it in `<span class="icon">` and style that. A **bare** `:global(.icon)` leaks app-wide; only a compound form (`.parent :global(.icon)`) is safe. Same trap one level up: an icon arriving through a snippet from a parent (`DashboardCard`'s `icon` snippet) renders with the *parent's* scope hash, so a plain `.card-head-title svg` in the child never matches - it has to be `.card-head-title :global(svg)`.

- **`app.css` dark theme** is defined twice (media query + `[data-theme='dark']`), and `index.html` has a blocking inline `<script>` setting `data-theme` before first paint; both intentional (explicit choice beats system preference, and it avoids a theme-flash). Keep the `localStorage` key in sync between `index.html` and `theme.ts` if it changes.

## Design Details

### `internal/taganalyzer`

Pure tag-string analysis (`tokenize → classify → family → order`), with no I/O.

This is one of the most important components in DockVMap. It determines which tags are grouped together, which tag in a family is newest, how families are presented in the tag picker, and whether `updateAvailableFor` reports an available upgrade. Errors here usually produce a wrong recommendation rather than a visible failure, so correctness is critical.

`updateAvailableFor` (`internal/service/images_refresh.go`) skips a newer same-family candidate when the pinned tag's version axes are a prefix of the candidate's: every axis of the pinned tag is a numeric prefix of the candidate's corresponding axis, and the candidate is more specific somewhere (an axis is longer, or the candidate has extra trailing version axes the pinned tag lacks). So pinned `1.2`, candidate `1.2.6` is not an upgrade since `1.2` already tracks it; `1.3.0` still is; `17-alpine-3` does not flag `17.9-alpine-3.23` (prefix on both the app and base axes) while `17.10-alpine-3.23` / `18.x-alpine-3.23` still do; and pinned `10.11` does not flag `10.11.11.20260606-153911` (a dated build - same `10.11` prefix plus an extra time axis), the same way it already does not flag clean `10.11.11`. The comparison runs off `image_tags.version_segments`, a per-tag JSON snapshot (`[][]int64`) of every `OrderVersion` segment's `Numbers` in order (empty for non-version axes, so date/alphabetical families are unaffected), written by `imageTagsFromAnalysis` alongside `family_id`/`tag_order`/`prerelease`. A base-image-only bump at the same app version (`17.9-alpine-3.23` → `17.9-alpine-3.24`) is not a prefix relation, so it is still reported. This suppresses the recommendation, not the ordering: when a real version gap exists and the newest tag is a dated build (`10.11.5` → a dated build of `10.11.11`), an upgrade is still reported, just pointed at the snapshot rather than the clean tag.

Before changing grouping, classification, or ordering, re-measure with `go run ./cmd/tagaudit` (`-verify` for the invariants, accuracy and determinism, `-shapes` and `-rank` for what regressed), and keep every invariant counter at zero. Also bump `taganalyzer.AnalysisEpoch`: `internal/service/images.go`'s tag-refresh skip caches the analysis by input tag set (`images.tag_set_hash`), and the epoch is folded into that hash so a logic change forces every image to re-analyze on its next sweep.

#### Guarantees

The analyzer guarantees:

- Every tag belongs to exactly one family.
- Family IDs are unique within a repository.
- A family never mixes different values of a literal/named segment.
- Ordering never inverts the leading version.
- `Analyze` is deterministic: the same tags in any input order produce a byte-identical result.
- Results are safe to compute concurrently.

These invariants have been verified against hundreds of thousands of real tags across ~200 repositories, and re-verified against a separate randomly sampled corpus of similar size that the analyzer was never tuned on: zero violations in both. Re-verify with `cmd/tagaudit -verify` after any change.

A `Family` (`Kind`: `blood` / `ancestor` / `step`) represents a **structural lineage**, not runtime compatibility. It means the tags appear to be versions of the same named thing (same repository, OS base, variant, etc.). The analyzer cannot determine whether two versions are actually compatible, so it must not use compatibility assumptions to exclude a match. Whether an upgrade is safe remains the user's decision; `updateAvailableFor` only surfaces the newer tag as a suggestion.

Only version-shaped segments (numbers or dates) may vary within a family. Literal/named segments such as `noble`/`jammy` or `jdk`/`jre` must match exactly and are never treated as upgrade axes.

#### Blood families

`blood` is the strongest family relationship: every member must have an identical computed identity pattern.

The identity pattern is based on segment shapes rather than literal values. Version segments collapse to `solo`, `multi`, or `calver`; prefixes and suffixes remain literal; date/time segments collapse to a constant; confirmed hash segments also collapse to a constant.

A bare number such as `11` is treated as a multi-part version only when `collectKnownMajors` finds evidence that `11` is a real major version elsewhere in the same repository, such as `11.0.24`. This evidence is scoped to the preceding segment context rather than the raw segment index, preventing unrelated tag shapes from influencing one another.

Hash-shaped segments are normalized only when `collectHashLengths` confirms the slot from the repository's own tag set: at least 5 distinct values of the same length at the same position, with at least one containing `a`–`f`. This prevents long numeric build counters from being mistaken for hashes.

Hash-shaped means `^g?[0-9a-f]{7,40}$`. The optional `g` covers the abbreviated SHA produced by `git describe --tags`, such as `v3.29.6-1-gb73411456155`.

There is deliberately no additional ratio/frequency heuristic. An earlier ratio-based guard performed worse on repositories with architecture fan-out, so it was removed after testing across the corpus.

Hash normalization happens at identity time rather than classification time. `normalizeSegments` initially parses numeric tokens as versions; once repository statistics are available, `normalizeHashSegments` rewrites confirmed hashes as literals. This also prevents commit SHAs such as `a953921` from being ordered numerically as if they were versions.

#### Ancestor families

`ancestor` connects a root family to another family when the root's pattern unambiguously extends into exactly one target via `isSkeletonExtension`. Only variable segments with no prefix/suffix or statistically confirmed hashes may be skipped.

A hash-free root never merges into a family whose varying axis is a hash. Otherwise release families can absorb commit builds and expose a SHA as an upgrade.

A version segment is also never skipped when the root's next segment is itself a version. This prevents a real version component such as a JDK major from being confused with a later build number.

Root candidates are tried longest-pattern-first so more specific families claim targets before shorter patterns. Merged families use their most general member as `rootRep`, and `attachAncestors` repeats the process until no further merges are possible.

Ambiguity always loses: zero or multiple matching targets leave the root unchanged. A later pass may resolve the relationship after competing families have themselves merged.

#### Family relevance

Families are ordered by `familyRelevance` rather than by `Kind`. How a family was constructed does not determine how useful it is to a user.

Relevance is evaluated from the family's root, using these criteria in order:

1. A singleton never leads.
2. A root without hash literals beats a commit-built root.
3. Version-led beats date-led, which beats alphabetical-led.
4. Fewer root segments beat more.
5. A multi-part version with a plain or `v` prefix beats a named version such as `alpine3.24`, which beats a bare integer/build counter.
6. More tags beat fewer.
7. The family key breaks remaining ties.

These rules were tuned against `sampledata/`. Across the sample corpus they changed the leading family in a few dozen repositories, all changes improvements or neutral, with no repository left leading with a singleton. Retune against the corpus rather than a single repository.

#### Family identity and ordering

`Family.ID` is an FNV-64a hash of `Family.Key`, masked to 52 bits so it stays JSON-number safe. It is not a per-run counter, so a family keeps the same ID across refreshes as long as its pattern is unchanged.

`Family.HasOrder` is false when the only varying axis is a confirmed hash. Such tags can still be ordered for display, but the order has no semantic meaning, so `updateAvailableFor` does not report an upgrade for the family.

Anything that cannot be related to another tag becomes an isolated singleton. It retains `Kind: FamilyStep` for frontend/backward compatibility, but this no longer represents a weak grouping relationship; it simply means no relationship was claimed.

#### Recognized version conventions

In addition to standard `MAJOR.MINOR.PATCH`, the parser recognizes several glued suffix conventions that affect grouping:

- PEP 440 `aN` / `bN` pre-releases
- OpenBSD/OpenSSH-style `pN` patches
- Pre-JEP 223 Java `uN` updates, such as `8u422`
- Alpine/apk `-rN` package revisions
- Debian/Ubuntu same-day rebuild suffixes such as `20180112.1`

The Alpine revision is absorbed into the preceding version, so `1.2.3-r1` stays in the same family as `1.2.4`. A leading branch number such as `r409-...` is unaffected. Likewise `20180112.1` is the same date identity as `20180112`, with `.1` affecting ordering but not family identity.

### Image tag refresh

Every trigger (worker `RefreshAll`, `-refresh-tags`, `Images.Create`, the GUI's manual refresh) goes through `RefreshAvailableTags` (`internal/service/images_refresh.go`). It takes the per-image lock (`imageRefreshLocker`, shared with `UpdateTag`/`Rename`), wraps its body in a 10-minute `context.WithTimeout`, and sets `images.refresh_status` to `running` on entry / `idle` on exit, the exit write via `context.WithoutCancel` + 5s so a shutdown mid-refresh can't strand the row at `running`.

`imageRefreshLocker` is the real serialization guarantee; `refresh_status` is only a best-effort UI hint (the entry/exit writes aren't CAS, so a concurrent worker refresh finishing first can clear a GUI-initiated claim, which is harmless, at worst a redundant refresh).

The GUI's `POST /images/{id}/refresh-tags` calls `Images.StartBackgroundRefresh`: `TryStartImageRefresh` CAS-gates `refresh_status` `idle`→`running` (0 rows ⇒ a worker or manual refresh is already running ⇒ `202 {status:"running"}`), then the refresh runs on `Images.bgCtx`, not `r.Context()` (which dies at the web server's 45s `WriteTimeout` and on client disconnect), untracked by `runScheduledJobs`'s WaitGroup like discovery scans. The handler polls `refresh_status` for ~2s (150ms) before falling back to `202`; a finished refresh returns `200 {status:"refreshed"}` or `{status:"error", error}` (from `last_check_error`). Manual refresh uses `RegisterEvent: EventSilent` / `FlagAsNew: true`, so no notifications, unlike the worker's `EventNormal`.

`Images.RecoverFromRestart` (startup, beside `Discoveries.RecoverFromRestart`) is the only recovery path, resetting any `running` left by a hard crash or clean shutdown mid-refresh back to `idle`.

**Pinned images:** `images.pinned` (the details-page toggle, `PUT /images/{id}/pin` → `Images.SetPinned`) means "stay on the current tag, stop the update nagging". The refresh still fetches, filters, analyzes, and stores tags and still emits `TAG_ADDED` / `TAG_REMOVED`, but `effectiveUpdateAvailable` (the single wrapper both `RefreshAvailableTags` and `UpdateTag` call around `updateAvailableFor`) returns `(false, "")` for a pinned image, so `update_available` / `update_available_tag` stay cleared and no `UPGRADE_AVAILABLE` event fires. `SetPinned` recomputes through the same wrapper in one transaction: pinning clears the flag, unpinning re-derives it from the already-stored tags (no upstream fetch), the way `UpdateTag` recomputes silently with no event. The images list filter gains a `pinned` status and the row shows a "Pinned" badge instead of "Up to date" / "Update to X".

**Current digest** (`images.current_digest` / `current_digest_tag` / `current_digest_since`, migration `031`, `internal/service/images_digest.go`): the digest the image's selected tag points to upstream. `RefreshAvailableTags` sends one `HEAD` for the selected tag only (`oci.Client.ManifestDigest`), after the tag list and before the unchanged-tag-set early return, so a tag republished under the same name is still caught. The `Accept` header lists the OCI index, Docker manifest list, OCI manifest and Docker v2 manifest types, the same set Docker sends, so a multi-arch tag returns the index digest, which is what a host records in `RepoDigests` when it pulls by tag (both the classic and containerd image stores). On Docker Hub a manifest `HEAD` does not count against the pull limit. Each lookup is capped at 10s (`digestLookupTimeout`) on top of the client's normal retries, so a registry that rate-limits manifest requests adds at most that per image. A missing `Docker-Content-Digest` header is stored as unknown (no `GET` fallback); a malformed one or a failed request records a `digest` row in `background_failures`, keeps the last digest and never fails the tag check. `UpdateImageDigest` writes only when the digest or its tag changed, only while `images.tag` still equals the looked-up tag, and never touches `updated_at`; `current_digest_since` is when that tag and digest pair was first seen. A tag change (`notifyTagChanged`, after the commit) starts one background lookup per moved image, so the new tag's digest is known within seconds instead of at the next sweep. Readers trust the digest only when `current_digest_tag` equals `images.tag`; `newImageResponse` omits it otherwise, and Image details shows the short digest with "first seen", or "Unknown". After a tag change made from Image details, the page reloads the image once more 2s later if the digest isn't known yet. **Served digest:** a successful manifest `HEAD` or `GET` for the image's tag (the virtual tag or the tag itself, not a digest) whose `Accept` lists an index type (`oci.AcceptsIndex`, the same index types the lookup sends) reports the response's `Docker-Content-Digest` to `ProxyUsage.RecordTagDigest` when it differs from `Image.TagDigest()`. The proxy always fetches a tag live, so without this a tag republished upstream between two checks made every host that pulled it read Outdated until the next check. A client that can't take an index would get one platform's manifest, whose digest isn't the tag's, so it reports nothing. `ProxyUsage` keeps one entry per image (the first time that tag and digest were seen), `proxy-metrics-flush` saves it through the same `updateImageDigest` rule as the lookup (only while `images.tag` still matches, only when it changed), and `ApplyToImages` and `Hosts.track` (`ApplyTagDigest`) overlay it until then.

**Current tag gone:** when the registry's tag list (before tag filters) no longer has the selected tag, the check stores "tag X no longer exists in the registry; pick another tag" as `last_check_error`, records it in the failure log (source `refresh`), and skips the digest lookup for that tag. `ListTags` fails instead of returning a partial list, so a missing tag is really missing. A tag change (`applyTag`) on an image that has a check error starts the normal background check (`StartBackgroundRefresh`), so the error clears within seconds once the new tag exists; images without an error only get the digest refresh, as before.

**Frontend:** `ImageDetails.svelte` polls `GET /api/images/{id}` every 2s while `refreshStatus === "running"`, via `createPoller`. It merges each poll into `image` field-by-field (`mergeImage`) instead of reassigning, so a `refreshStatus`-only tick doesn't churn child props. The change-tag modal fires the action (toast, no picker reload on `202`) and takes `refreshStatus` as a prop, swapping its Refresh button for `<RefreshingIndicator>` while running, then reloading its picker once (keeping the selection) when the prop returns to `idle`; the last-check-error row's refresh button is hidden the same way. (`@keyframes spin` / `.spin` are global in `app.css`.)

### Image groups

A group keeps images that release together on one version (Nextcloud AIO's six images, Immich's server and machine learning). It is a strict lock: members always share `images.tag` and `images.pinned`. The tag stays on each image rather than on the group, so the proxy's resolve path and the refresh pipeline do not know groups exist. An image is in at most one group. Membership is manual because a shared namespace does not imply a shared version (Grafana, Supabase, mailcow).

**Enforcement lives in `Images`, not the UI.** `UpdateTag` and `SetPinned` go through `lockImageScope`, which resolves an image to its whole group (or to itself when ungrouped) and applies the change to every member in one transaction, so `ChangeTagModal`, tag history restore and the Updates row cannot split a group. `GetTags` returns the tags on every member for a grouped image, which is how those callers offer only common tags without knowing about groups. Matching is by exact tag string; family and order come from a lead member (`groupLead`). `GroupTagUnavailableError` wraps `ErrTagUnavailable` and names the members missing a tag, and nothing is written in that case. Each member still gets its own history row and `IMAGE_TAG_CHANGED` audit row (with a `group` field).

**Locking.** Holding several per-image locks must not deadlock or outlive the 45s `WriteTimeout`, and a refresh holds its lock through the upstream fetch. So `lockAll` takes every lock with `TryLock`, releases all on any miss, retries for `imageGroupLockWait` (5s), then returns `ErrImageGroupBusy` (`409`). A single ungrouped image still blocks on its lock as before. `lockImageScope` re-reads the scope after locking and retries if membership changed.

**State is computed on read.** `images.update_available` stays per member and refresh is untouched, so tag events stay per image. Webhooks fire per image; emails collapse a group into one digest line (see `notification_digest.go`). `applyGroupState` derives the group's state: flagged when any member is flagged, `UpdateAvailableTag` is the newest upgrade candidate present on every member, and `PartialTag` is a newer tag only some members have. Flagged with no `UpdateAvailableTag` is the blocked state. It must stay visible because a replaced member (Harbor's `redis-photon` stopped at `v2.15.1` when `valkey-photon` took over) would otherwise silence the group forever.

**Membership.** `saveGroup` validates and writes name, membership, tag and pin in one transaction, holding the locks of old and new members. Joining moves an image to the shared tag. Any pinned member pins the whole group, since a pin is an explicit decision not to move. A removed image keeps its tag and pin. Deleting a group keeps its images (`ON DELETE SET NULL`), and deleting the last member deletes the group.

**Proxy.** `resolveCache` holds an image for 20s, which would let a `compose pull` mix versions right after a group change. `Images.OnTagChanged` invalidates the changed names after commit. A generation counter stops a lookup that started before the commit from re-caching the old tag.

**Refresh.** `StartBackgroundRefresh` on a grouped image refreshes every member sequentially with the requested image last. Its `refresh_status` was already claimed as `running`, so that one status covers the whole group for the existing pollers.

**Frontend.** `ImageGroupModal.svelte` creates, joins and manages groups from `ImageDetails` and the Updates row; `GET /api/image-groups/common-tags?imageIds=` feeds its picker for a membership that does not exist yet. `routes/Groups.svelte` (`/groups`, in the sidebar) lists every group with its shared tag and status; a row opens the same modal, its image names link to `/images?group=<id>`, and flagged groups link to `/updates?search=<name>`. `suggestImageGroups` (`lib/utils/imageGroupSuggestions.ts`) offers ungrouped images with the same registry, namespace and tag as a one-click group; floating tags like `latest` are skipped because sharing one says nothing about sharing a version, and dismissals are per browser in `localStorage`. Rows on the Virtual Images list stay one per image, so pagination and per-image status keep working: a grouped image gets a label that opens the modal in place, a Group filter appears once groups exist (`groupId`, or `ungrouped` for "Not in a group"), and the list search also matches group names.

### Tag discovery

`internal/service/discoveries.go` (table `tag_discoveries`) backs the "Add virtual image" wizard's repository step.

`Check` does a cheap single-page `oci.Client.CheckRepository` first, never the full `ListTags` pagination, so a huge repository can't make "check repository" itself slow. The real scan runs in a goroutine off the worker context (capped at 10 minutes, recovers its own panics), writing into a `tag_discoveries` row keyed `UNIQUE(registry_id, repository)`; that row is both the cache (TTL'd via `tag_discovery_ttl`, refreshed in the background without clobbering the previous result on failure) and the dedup lock (insert-or-reclaim on conflict, so concurrent requests for the same pair converge on one scan).

`Check` waits inline on the row for ~2s before falling back to `status: "running"` for `GET /api/discoveries/{id}` to poll, so small/cached repos still resolve in one round trip. `RecoverFromRestart` (startup) fails any row left `running` by an unclean exit; the `tag-discovery-cleanup` job prunes terminal rows older than 7 days. Shutdown does not wait on in-flight scans (see [Background worker](#background-worker)).

`Images.Create` takes an optional pre-fetched `availableTags`, filled from a completed discovery's cache by `apiCreateImage`, so saving doesn't re-trigger the scan `Check` just avoided. Live progress (`tagsSeen`) lives only in an in-memory map on `Discoveries`, updated via `ListTagsWithProgress`'s per-page callback and never persisted, since the scan and the polling handlers share one process. `raw_tag_count`, captured alongside `tag_count` on completion, drives the response's `ignoredCount`.

Any user-suppliable registry host must be checked against already-configured registries (`GetRegistryInfoByHost`) before the server requests it (see [Traps](#traps)).

### Hosts and the agent

Visibility only: the agent reads Docker and answers, the controller (dockvmap) polls, stores and compares. The controller connects to the agent, never the other way, so a host network (a DMZ) never needs a route to the controller, and the agent has no write path to Docker to protect.

**Packages.** `internal/agentapi` is the wire contract shared by both sides: `AdoptPath` / `SnapshotPath`, `DefaultPort` (`9002`), `ProxyHostHeader`, `ProtocolVersion`, the `Adoption` / `Report` / `Error` shapes, the limits (`MaxContainers` 1000, `MaxImages` 2000, `MaxTextLength` 255), `ParseImageRef` / `ImageRef.OnHost` (one image-reference rule for both sides; a registry host on `:443` matches a portless one), and `identity.go`: `NewIdentity` (self-signed ECDSA P-256, cert + key in one PEM, valid until 9999 since it is pinned, not chained), `ParseIdentity` and `Fingerprint` (`sha256:` + hex of the certificate, so `shortDigest` displays it). `internal/agent` imports only `agentapi` and the standard library, so the agent binary stays small and never links the controller. `internal/agentclient` is the controller's side of the wire. `cmd/dockvmap-agent` is the entry point (`-version`, `-data-path` with a build-time default like the controller's: `./data`, `/data` in the image, `slog`, `signal.NotifyContext`).

**Pairing.** Mutual TLS with pinning, TLS 1.3 only, no tokens. The agent keeps `agent.pem` (its identity) and `paired.json` (the controller's fingerprint) in its data path, written atomically. The controller keeps `<data-path>/agent_client.pem` (`loadAgentClientIdentity` in `bootstrap.go`, generated like the credential key, listed by `-backup`), and per host `address` and `agent_fingerprint`. The agent requires a client certificate on every connection (`RequireAnyClientCert`) and checks it in `authorize` before routing: unpaired, only `adopt` is served (`409` otherwise); paired, a different fingerprint gets `403`. `adopt` pairs with the first caller and is idempotent for that caller. The client (`agentclient.Client.do`) skips chain checks and pins in `VerifyConnection`: with a stored fingerprint a mismatch is `ErrIdentityChanged` and the handshake aborts before any request; with none it records what it saw, which `fetch` stores (adopt on first contact, since adding a host with its address is the consent). `403` maps to `ErrPairedElsewhere`, `409` to `ErrNotAdopted`; an agent that lost `paired.json` but kept its certificate is adopted again on the spot, since the pin still holds. An identity change is never accepted silently: `TrustNewAgent` (audited `HOST_AGENT_TRUSTED`, only while the host shows the change) clears the pin, and the poll it runs adopts whatever answers. One TLS connection per poll (`DisableKeepAlives`), so there is no pool to go stale and the pin is checked on every poll.

**Polling** (`hosts_poll.go`; host records, status and version tracking stay in `hosts.go`). The `agent-poll` job runs `PollAll` every `agents_poll_interval` (default 30s), up to 8 hosts at a time with a 10s timeout each. `poll` holds a per-host lock, so the job and a live poll never run together, and skips a host polled less than `maxAge` ago. `GET /api/hosts/{id}` polls first (`livePollMaxAge` 5s, `livePollTimeout` 3s) unless the host's last poll failed, and skips it when a poll of that host is already running (`TryLock`), so Host details is live while a down host never stalls the page; the background poll handles it. `fetch` only talks to the agent and returns the fingerprint it adopted, which `poll` saves even when the snapshot right after fails, since the agent is paired by then. `Snapshot` sends the stored `report_fingerprint` as `If-None-Match` and the proxy address (`config.ProxyPublicAddress`, for `DOCKVMAP_AGENT_PROXY_ONLY`) in `X-Dockvmap-Proxy-Host`; the agent answers `304` when its snapshot's fingerprint (sha256 of the report JSON, also the `ETag`) is unchanged, which only touches `last_seen_at` (`TouchHost`). A changed report replaces the host's `host_containers` rows in one transaction (`ReplaceHostSnapshot`); a report that carries a Docker error keeps the last known containers and info (`RecordHostDockerError`). Every successful write clears `poll_error` / `poll_error_kind`; a failed poll records them (`RecordHostPollError`: `failed`, `identityChanged` or `pairedElsewhere`) on the host, never as a job error and never in System > Failures, since the Hosts page already shows it. Only store errors fail the job. Logging is per change: a new error message once, `host agent answers again` on recovery. Reports are validated in `snapshotFromReport` (counts, text lengths, ports ≤ 100 per container, `tcp`/`udp`/`sctp`, IPs ≤ 64 chars), bodies are capped at 8 MiB, and a bad report is a poll error, never a partial write. Container state is bounded text, not an enum, so one state dockvmap has never seen can't reject a whole host's report. A different `ProtocolVersion` is refused, but `checkAgent` still records the version, so the UI says "Update agent" instead of just "Offline". Bump `ProtocolVersion` only for an incompatible wire change; additive optional fields don't need it. Addresses are normalized on save (`normalizeAgentAddress`: `host` or `host:port`, bare IPv6 accepted, `:9002` added when missing), so the stored value is always dialable, and unique, so one agent can't be counted twice under one address. A timeout reads "the agent didn't answer in time", not Go's `context deadline exceeded`.

**Agent server** (`agent.go`, `server.go`). `Serve` runs the HTTPS server (header, read, write and idle timeouts, 64 KiB headers, the server's own log lines at debug so a port scan doesn't fill the log) next to `watchEvents` and an hourly cache reset. Events only invalidate the cache; the snapshot is built on each poll, serialized by `snapshotMu`. Only the container events in `containerChanges` (create, start, die, destroy, rename, pause, unpause, update, health_status) drop a cached container; `exec_*` from healthchecks is ignored. While the event stream is down (`dockerCache.watching` false), every poll resets the cache and reads Docker in full, so a missed event can't leave stale details. A Docker read failure is logged once per distinct error and once on recovery.

**Docker reads** (`docker.go`, `snapshot.go`). `GET`s only: `/version`, `/info`, `/containers/json?all=1`, `/containers/{id}/json`, `/images/json`, `/images/{ref}/json`, `/events`. API version 1.41, or the daemon's `MinAPIVersion` when that is higher, negotiated once under a mutex. Each call has a 5s timeout (`dockerRequestTimeout`), below the controller's 10s poll timeout, so a hung daemon comes back as a Docker error ("Can't read Docker", last known containers kept) instead of an agent that didn't answer. `dockerCache` keeps per-container details, the image list and `/info` between polls, so a steady host costs one container list per poll. Invalidation uses an epoch: every reset or forget bumps it, and a fill started under an older epoch is dropped (`write(epoch, fn)`), so an event arriving mid-fetch can't be overwritten by stale data. The event stream connecting resets the cache, since events may have been missed while it was down. A container's running image comes from `Config.Image` on inspect, not from the list, because the list shows a bare `sha256:` once the tag has moved. Only published ports are sent; env, mounts, other labels and logs never leave the host. A Docker failure is reported as `dockerError` with a hint (missing socket, permission, refused), so the UI shows "Can't read Docker" instead of silence.

**Version status** is computed on read (`track` / `trackContainer`), never stored, so a tag change shows on every host at once without waiting for agents. A container is tracked when its image host is the proxy (`ProxyTarget`, from `proxy_public_host` or the request host); the repository is looked up as a virtual image and compared with `Image.TagDigest()`, the single digest rule from 1.8.0: running digest matches → `upToDate`; a local image for the same reference has it → `pulledNotRecreated`; otherwise `outdated`; no digest on either side → `unknown`; repository not a virtual image → `unknownImage`. `knownDigests` also counts the image ID as one of its digests: on the containerd image store the ID is the manifest or index digest, and an image loses its `RepoDigests` once a pull moves its tag, so without it a container still on the old version would read `unknown` instead of `pulledNotRecreated`. On the classic store the ID is the config digest, which never equals a manifest digest. A tag other than the virtual tag sets `pinnedTag`. A host is online when a poll succeeded within 3 poll intervals (`hostOfflineAfterPolls`) on the current protocol and its agent wasn't refused (identity changed or paired elsewhere), and current (`Host.Current`) when it is also able to read Docker; anything else is last known data. `HostDetails` still shows those containers, marked as such, but they never count. The rollout (`model.Rollout`, "5/8 up to date") counts running or restarting containers that follow the virtual tag and have a known version (`ContainerTracking.InRollout`), on current hosts: a pinned or stopped container stays visible but would otherwise keep a rollout from ever completing, while a crash-looping one must stay in it so a bad deploy shows. `trackedContainers` loads them with one `ListAllHostContainers` query and tracks them; `Hosts.List` derives the per-host rollout, crashed and unhealthy counts and the last restart for current hosts, and `ImageRollouts` (`GET /api/images/rollouts`) the Deployed column on Virtual Images, with `HostsOffline` and `HostsDockerError` for hosts that ran the image at their last report but aren't current (offline or too old an agent, versus online but unable to read Docker), so a complete number can't hide a host nobody can check. The dashboard tile counts only current hosts and sums the outdated counts; its caption calls every other host "need attention" (offline, can't read Docker, never connected or too old an agent), and the Hosts page shows which. `Hosts.ImageContainers` returns the same rollout for Running on. `HostContainer.Crashed` is the single crash rule: dead, restarting, or a non-zero exit other than 137 and 143, which a plain `docker stop` produces. The Hosts badge counts a crash for `crashBadgeWindow` (7 days), or while it keeps restarting, so an old one doesn't stay red; the container stays listed in Host details, and `RecentlyCrashed` makes the Crashed filter match the badge. `listHosts` is the cheap variant with no tracking.

**Frontend.** `routes/Hosts.svelte` (rows open the host and carry no actions, as on Virtual Images; badges only show status, so anything clickable must look clickable; a muted hint appears when online hosts report containers but none came through the proxy address, the usual sign of a wrong `proxy_public_host`; the address comes from `proxyAddress` in `lib/utils/pullInfo.ts`, the one rule every pull command uses, which leaves out port 443), `routes/HostDetails.svelte` (host facts on one line under the title, address first and the agent's short fingerprint last; a notice per state, with Trust new agent for a changed identity and Compose file while waiting; Edit (name and address, `HostModal.svelte`, shared with Add host) and Delete in a Danger zone card at the bottom, like Image details; the Image column links containers pulled through the proxy to their virtual image in the accent colour (plain text when that virtual image was renamed or deleted, since blue means a link), shown as `name:tag` without the proxy address, which is in the tooltip, with a warning icon when it counts as outdated, and the version detail on hover; a detail page, so each section is a card, with Containers holding its own title and filters; one flat list sorted by name with search, Show and Stack filters; the stack chip sets the Stack filter), `lib/components/imageDetails/RunningOnCard.svelte` (one flat row per container, outdated first, then containers of hosts that can't be checked, which show the host's status and an Unknown version; refreshed every 15s, hidden while no host is configured), `lib/components/hosts/RolloutSummary.svelte` (the one "5/8 up to date" format), and the dashboard's Hosts tile. States render through the shared `StateIndicator.svelte` (dot + label + muted detail line); `containerState` and `formatPorts` in `lib/utils/hosts.ts` hold the display rules; version and crash rules come from the server (`tracking.needsUpdate`, `crashed`).

**Dev.** `make dev` also runs `make dev-agent` when `data/agent/` exists: the agent listens on `127.0.0.1:9002` with its state there; add a host `127.0.0.1` once in the dev UI. `internal/agent`'s tests run the real agent against a fake Docker on a unix socket, talking to it through `agentclient` (adopt, pinning, pairing with one controller only, restarts, `304`, the cache with and without events); `internal/service`'s host tests use a fake `agentDialer`. End-to-end checks use a real agent container against a scratch controller, never a second Docker daemon on the host network.

### Internal registry

DockVMap fronts one official `registry:2` on its stack network: names that aren't virtual images pass straight through to it, pushes included, so one proxy address serves pushes, real pulls and virtual tags. The registry stays the registry (storage, uploads, garbage collection); DockVMap adds TLS, proxy-token auth, an audit entry per pushed tag and a tag check after a push. Plain HTTP and no login to the registry, always: it's reachable only by DockVMap, and logins are DockVMap's job.

**Config.** `internal_registry.enabled` (default off) and `internal_registry.address` (default `registry:5000`, `host:port` with the port required, no scheme). This is the only switch; the UI can't change which registry is internal.

**Service** (`internal/service/internal_registry.go`, `InternalRegistry`). All of the feature's own logic:
- `EnsureInternal` at startup: validates the address with `validRegistryAddress` (config can't import services), then keeps one registry entry marked `registries.internal = 1` (partial unique index, migration `035`). It creates the entry, takes over an existing entry with that address, or moves the marked entry to a changed address (virtual images reference it by id, so they follow). It fails startup on an invalid address or when another entry already has the new address, and clears the mark when the setting is off. Every change is logged and audited without a user.
- `StartChecking`: a background `GET /v2/` until the registry answers. A failure is recorded once in the failure log (source `internal_registry`), retried every 10s, never fatal.
- `Pushed` and `Deleted`, called by the proxy after a manifest `PUT` by tag answers `201` or a manifest `DELETE` answers `202`: add the change to a per-repository pending list and restart that repository's timer, nothing else on the request path. The timer fires 5s after the last change, at most 30s after the first, or right away at 1000 pending; it writes the `IMAGE_PUSHED` / `MANIFEST_DELETED` audit entries (token label, client address via `WithRequestInfo`) and starts the existing `StartBackgroundRefresh` once for each virtual image on that registry and repository. `Stop` at shutdown writes the pending audit entries only, since the background workers have already stopped; the next scheduled check picks up those tags. A hard kill loses the last few seconds of audit entries, the same trade-off as `ProxyUsage`.
- `Repositories`: `_catalog`, following `Link` pages, up to 1000 names, for the suggestions in New virtual image.

`Registries.UpdateByID` / `DeleteByID` refuse the marked entry (`ErrRegistryManagedByConfig`, 409).

**Proxy** (`internal/proxy`). With the feature off, `ServeHTTP` runs exactly the pre-1.10 code path (`serveVirtual`, the early `405` for writes, the server's 15s `ReadTimeout`). With it on (`serveWithInternal`):
- `parseRegistryPath` (`path.go`) classifies every registry path: manifests, blobs, `blobs/uploads/`, `blobs/uploads/<id>`, `tags/list`, referrers, `_catalog`. The old split took the last two segments and misread upload paths. Unknown shapes get `404`; names failing `service.ValidRepositoryName` get `400 NAME_INVALID` without reaching the registry.
- A virtual image's name goes to the existing manifest and blob handlers; writes to it get `405 UNSUPPORTED`, except when the virtual image is built on the internal registry's repository of the same name (`myapp` on `myapp`): those writes pass through, apart from a manifest `PUT` of the virtual tag, which is refused. Any other name goes to the pass-through, and writes need a token with Can push when `proxy_auth` is on (`403 DENIED`).
- `passthrough.go`: `httputil.ReverseProxy` to `http://<address>`. The outbound `Host` is the registry's, the client's `Authorization` is removed, `FlushInterval: -1`, `ErrorLog` at debug. `ModifyResponse` rewrites a `Location` starting with `http://<address>` into a relative path (the registry builds upload URLs from its own host, which clients can't reach), turns a registry `401` into a `502` without `WWW-Authenticate` (otherwise Docker would start a login loop the registry can't satisfy), and hands successful tag pushes and manifest deletes to `Pushed` / `Deleted`. `ErrorHandler` always writes a response: `408` for an upload that ended early, the "didn't answer" `502` only for dial errors (`isDialError`), "ended the request early" otherwise. A virtual image whose upstream doesn't answer gets an OCI `502` naming that registry (`upstreamFailureMessage`), with the same "check that its container is running" message when it's the internal registry.
- Timeouts: the server's `ReadTimeout` is `0` when the feature is on, and each request sets its own 15s read deadline with `http.ResponseController`. Upload bodies are wrapped so the deadline moves a minute ahead while data arrives, so a slow large layer finishes and a stalled one is cut off. This works over HTTP/1.1 and HTTP/2.
- Virtual images whose registry is the internal one (`registryInternal`) skip the blob cache (`cacheFor`), since the registry is on the same machine. Pass-through requests don't touch the proxy counters (`totalRequests`, manifests, blobs) or `RecordImagePull`, so the dashboard stays about virtual images.

**Hosts.** A container on the proxy address whose name isn't a virtual image gets status `internalRegistry` (instead of `unknownImage`) when the feature is on, stays out of rollouts, and Host details says so in the image tooltip.

**Frontend.** Images carry `registryInternal`, and `utils/registries.ts` `imageSource` shows "Internal registry · team/web" wherever an image's source appears. Registries shows the Internal badge, the config note and, with `proxy_auth` off, the "anyone can push" warning; its edit window is read-only for the marked entry. New virtual image lists it first as "Internal registry (address)" (the picker is a native `<select>`) and passes catalog names to `Field`'s `suggestions` (a `<datalist>`). The audit tab shows "Token <label>" or "Anonymous" as the actor of `IMAGE_PUSHED` and `MANIFEST_DELETED`. The New token window shows Can push only while the internal registry is on; the internal registry's own window is read-only and titled "Internal registry".

## Conventions (backend, when adding code)

- **New JSON POST/PUT handler** → use `internal/web/api_routes.go`'s `decodeJSON[T](rw, r) (T, bool)`, don't hand-roll `MaxBytesReader`/`DisallowUnknownFields`.

- **New periodic background job** → append a `scheduledJob{…}` to the slice in `scheduledJobs` (`cmd/dockvmap/worker.go`); `run` is `func(ctx) (int, error)` returning the count to log against `doneMsg`. Each gets its own goroutine, `time.Timer` and `select`; never share one `select`. Set `onShutdown` if the job must do a final action on a clean stop; set `trigger` if it can be run early on demand. The `name` is the `worker_ticks` key; keep it stable and unique. A new service the job needs goes on the `workerDeps` struct, not a new positional arg.

- **New store constraint check** → use `isUniqueConstraintErr`/`isForeignKeyConstraintErr` (typed `sqlite.Error.Code()`), never match on `err.Error()` text.

- **New audit-worthy action** → call `recordAudit`; actor/request info comes from `context.Context` (`service.RequestInfo`/`CurrentUser`), never pass as params.

- **New list filter** → embed `model.Pagination` into a per-domain filter struct (see `model.ImageListFilters`); don't add a shared generic `Filters` type.

- **New sortable list** → embed `model.Sort` next to `model.Pagination` in the filter struct, parse it with `parseSort(r, fields...)` (`internal/web/sort.go`, `sort` + `order=asc|desc`, unknown values are a `400`), and give the store query a `sortSpec` (`internal/store/querybuilder.go`): each field maps to a fixed SQL expression, `nullable` sorts missing values last in both directions, `fallback` is the list's existing order (used when no sort is chosen, so the API default never changes), and `tieBreak` keeps paging stable. Field names live in `model` (see `model.ImageSortFields`) so the handler and the store share them. No request value ever reaches the SQL. Frontend: spread `NO_SORT` into the `createListView` defaults, pass `sortFields` (field → first-click direction), add `...sortParams(q)` to the fetch, and render `SortableHeader` for each sortable column.

- **New date-range filter** → bind through `internal/store/querybuilder.go`'s `sqliteDatetime()` (see [Traps](#traps)).

- **New cross-cutting web-layer dependency** (a service the HTTP handlers need) → add a field to `web.Dependencies` (`internal/web/handler.go`), not a new positional parameter to `web.New`/`newWebServer`. Same rule for the multi-dependency service constructors that already use a config struct: `service.NewImages(ImagesDeps{…})`, `service.NewDiscoveries(DiscoveriesDeps{…})`, `scheduledJobs(workerDeps{…})`.

- **Comments**: a short one-liner is fine where a WHY is genuinely non-obvious; never multi-line/paragraph comments.

## Traps

- **A `httputil.ReverseProxy` `ErrorHandler` that returns without writing answers `200 OK`.** When a read deadline cuts off an upload, Go cancels the request context first, so the handler sees "context canceled"; returning early there told the client a broken upload had succeeded. Always write a status. `ReverseProxy` also wraps the request body before calling the handler, so don't type-assert your own body wrapper there.

- **Interim `1xx` statuses reach wrapped `ResponseWriter`s.** `ReverseProxy` forwards `100 Continue`; a wrapper that treats the first `WriteHeader` as final logs `100` and stops a later panic from answering `500`. `httptest.ResponseRecorder` also treats a `100` as final, so test this with a real server.

- **`sqliteDatetime()`**: several tables set timestamps via SQLite's own `DEFAULT CURRENT_TIMESTAMP`, not Go. The driver's default `time.Time` formatting doesn't lexically compare against SQLite's stored format, so always bind through `sqliteDatetime()` for a date-range filter. (Canonical explanation; the Conventions entry points here.)

- **`//go:embed dist/*`** needs a non-dot-prefixed file under `dist/` at build time or the build fails outright; a bare `go build ./...` on a fresh checkout fails until the frontend has been built once. See [Commands](#commands).

- **SSRF**: any user-suppliable registry host must be checked against already-configured registries (`GetRegistryInfoByHost`) before the server requests it (see `Discoveries.Check`).

- **`trusted_proxies` append vs passthrough**: it only protects you if the reverse proxy in front **appends** to `X-Forwarded-For` rather than passing the client's own header through unchanged, e.g. nginx's `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`, not `$http_x_forwarded_for`. Get that backwards and an attacker's self-supplied header is trusted verbatim, silently defeating both the login rate limiter's per-IP accounting and the audit log's IP field. This is a deployment misconfiguration, not something dockvmap can detect. The `gateway` token (see `internal/web`) only helps if the published port is reachable *only* through the proxy; otherwise a direct hit is also SNAT'd to the gateway and its forged header is trusted.

- **Single-user model, no roles yet**: there's deliberately no create/list/delete-other-account API. Don't add one without checking first; it was removed on purpose.

- **`RegistryOptions` JSON keys are snake_case** while the rest of the API is camelCase (inherited from the Go struct tags); don't "fix" it in just one place.

- **`rewriteTimestamp`** (`tokenizer.go`) folds an ISO 8601 timestamp into the bare 14-digit form **before** tokenization, since the classifier only understands `20060102150405`. It covers the compact `20240101T120000`, the punctuated `2024-01-01T12-00-00`, and either with a leading label (`RELEASE.…` or `RELEASE-…`). `pretokenize` applies every rewrite in sequence rather than stopping at the first match.

- **`taganalyzer`'s tokenizer only splits on `-`/`_`, never `.`**: deliberate, since a version's own dots (`1.2.3`) must stay inside one token. A repo that uses `.` to glue on a non-numeric qualifier (`confluentinc/cp-kafka`'s `7.0.10.amd64`) is handled by `splitDottedToken`, which splits at the rightmost dot where one side is a recognizable shape - so `7.0.10.amd64` tokenizes as `7.0.10` + `amd64`.
